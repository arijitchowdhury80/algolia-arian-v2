# PRISM Multi-Tenancy: Breakpoints + Cost Curve (1 → 5 → 10 → 20 tenants)

**Date:** 2026-07-02
**Feeds:** `docs/plans/2026-07-02-cassandra-airtight-pipeline-goal.md` §5 (PART 2 design doc questions: shared-resource scaling for browser/bot-wall + SimilarWeb HITL, what-breaks-first, infra cost curve)
**Ground truth used (not re-derived):** §1.3, §1.4, §3, §5, §9-10 of the goal plan — box = 1 Hostinger VPS, 2 vCPU / 8G RAM / 96G disk (67G used, 30G free); bot-walls = detect+flag $0, no paid proxy (LOCKED); SimilarWeb = HITL same-IP login via noVNC or live-view browser (LOCKED); runtime cost per audit ≈ Claude subscription (flat, `CLAUDE_CODE_OAUTH_TOKEN`) + pennies of Gemini; 20 AEs, each 5-50 audits/yr → 5-20 audits/day peak across all.

## 1. Shared-resource scaling: browser/bot-wall + SimilarWeb HITL

### 1.1 SimilarWeb HITL — the good news: it does NOT scale with tenant count

The SimilarWeb fragility is a **session-identity** problem, not a **query-volume** problem: a login from Arijit's IP, then automated replay from the VPS's (different) IP, triggers SimilarWeb's "impossible travel" session kill. The fix already locked in the goal plan — same-IP login (noVNC into the VPS itself, or a live-view cloud browser where login and replay both originate from that browser's IP) — solves this once, for one shared session, regardless of how many tenants are behind it.

**Shared account vs. per-tenant login — practical answer: share ONE login.** This isn't the "20 humans sharing one paid seat" ToS problem (that's a per-human-license violation pattern). Here it's one authenticated automation session doing lookups on behalf of the platform, with one human (Arijit) periodically re-authenticating it. Buying 20 SimilarWeb seats to avoid this would be needless — SimilarWeb Pro/Team seats run in the hundreds of dollars per month per seat with enterprise-negotiated pricing, and per-tenant licensing buys isolation SimilarWeb itself doesn't require for read-only domain lookups.

**Why volume isn't the constraint:** each audit needs roughly one SimilarWeb domain lookup (2-4 pages captured: overview, traffic sources, audience/demographics). At 20 tenants' full peak (5-20 audits/day), that's at most ~20-40 domain lookups/day — trivial against typical Pro/Team monthly tracked-domain allowances. **Session lifespan is time-based (days to ~2 weeks per the plan), not query-count-based**, so the login cadence stays roughly constant (~1 login every 1-2 weeks) whether 1 tenant or 20 tenants are behind the session. The human-in-the-loop bottleneck genuinely does not grow with tenant count — this is worth stating plainly in the design doc as a non-problem, since it's easy to assume "20x tenants = 20x logins."

**What DOES scale: the queue, not the login.** Only one browser context can hold the authenticated session at a time (it's a single login identity), so SimilarWeb captures across tenants serialize. Each capture (navigate + screenshot 3-5 pages) takes roughly 1-3 minutes. Even at 20 tenants' absolute peak (20 audits/day all needing traffic data), that's ~20-60 minutes of serialized capture time in a day — not a bottleneck by itself. The only failure mode is if the traffic step is made *blocking* for the rest of an audit's pipeline; it shouldn't be — queue it as an async step so 20 audits can proceed through their other phases while traffic captures drain through the one shared session.

**noVNC (VPS) vs. Browserbase/Steel live-view, at N tenants:** noVNC is $0 (uses the existing box) but requires Arijit to VNC/SSH-tunnel in from his phone — clunky, and ties up a full desktop-class Chrome+X11 session (higher RAM footprint than headless, ~300-500MB) on a box that's already resource-constrained (§2). Browserbase's **Developer plan ($20/mo, 25 concurrent browsers, 100 browser-hours included)** gives a shareable clickable live-view URL — dramatically better for "Cassandra Telegrams Arijit a link, he taps it on his phone." Since only **one concurrent SimilarWeb session is ever needed** (shared login, serialized queue — see above), this is **not a scale-driven upgrade** — Developer tier at $20/mo is sufficient from 1 tenant through 20 tenants. Recommend switching off noVNC to Browserbase Developer at the first sign of noVNC friction, independent of tenant count. [Browserbase pricing, accessed 2026-07-02](https://docs.browserbase.com/guides/plans-and-pricing)

### 1.2 Bot-wall detect+flag at scale

Per-tenant honesty reporting (each audit records its own `BLOCKED_BY=<vendor>` flags) is pure per-audit data — it doesn't need shared-resource scaling, since it's just a boolean/enum written per module run. The only shared resource in play is the browser concurrency itself (headless Chrome instances running the detector + screenshot capture), covered in §2 below as the real constraint. The $0-spend decision (no proxy/unblocker) holds at any tenant count — cost doesn't change with scale, only the volume of `UNAVAILABLE(BLOCKED_BY=...)` flags being honestly reported does.

### 1.3 Browser capacity on 2 vCPU / 8 GB

Headless Chrome under active page load + JS execution + screenshot capture realistically costs 300-600MB RAM and is CPU-hungry (not just memory-hungry) per instance. Background services already resident on the box (Postgres, Redis, Caddy, Scout, 2x Hermes containers, FastAPI, runner, chat-proxy) plausibly consume 2-3GB baseline, leaving ~5GB headroom. **RAM would technically allow 2-4 concurrent audit browser phases; 2 vCPU will not** — Chrome's CPU draw during page load/JS execution means genuine parallelism collapses around 2-3 concurrent full pipeline runs before response times degrade sharply system-wide (including Cassandra's own chat responsiveness, since she's on the same box). This is the physical ceiling behind the "what breaks first" ranking in §2.

## 2. What breaks first — ranked by tenant count, with mitigation + cost

| Rank | Breakpoint | Bites around | Why | Mitigation | Cost |
|---|---|---|---|---|---|
| 1 | **Claude subscription concurrency** (the flat-rate `claude -p` runtime model) | ~3-5 tenants | The runtime-cost model (`CLAUDE_CODE_OAUTH_TOKEN`, flat subscription, no per-token billing) assumes low concurrency. Anthropic doesn't publish a hard "N concurrent sessions" cap for Max plans, but Max tiers meter usage in rolling session windows — 2-3+ simultaneous 30-90 min `claude -p` audit sessions on ONE subscription risks burning the window and getting throttled mid-audit. This is the first wall because it's a **policy/architecture ceiling**, not a hardware one — it hits even if the VPS has spare capacity, the moment 2+ AEs' audits genuinely overlap in time. **UNVERIFIED — Anthropic does not publish a concurrent-session limit; this needs an empirical test (fire 3 concurrent `claude -p` sessions on one Max 20x subscription and watch for throttling) before treating it as fact.** | Hard-cap the orchestrator's queue to N concurrent `claude -p` slots per subscription (test to find real N); add a 2nd subscription or API pay-per-token overflow path once the queue depth demands it. | 2nd Max 20x seat ≈ **$200/mo** if needed; API overflow is pay-per-audit (rough order-of-magnitude, not vendor-quoted: a few dollars per audit at Sonnet-tier token rates for the overflow-only audits) |
| 2 | **VPS CPU (2 vCPU)** | ~5-8 tenants | Headless Chrome + `claude -p` are both CPU-bound during active phases (§1.3). This is the hard physical ceiling on how deep the queue in Rank 1 can safely run, regardless of subscription headroom. | Move audit-worker browser+claude execution to a **separate VPS** (or 2-3 small worker boxes) so CPU contention there doesn't degrade the always-on Postgres/Caddy/Hermes-chat box; horizontal small boxes beat one bigger box for CPU-bound Chrome workloads (diminishing returns scaling vCPU vertically for this workload shape). | 1 extra Hostinger KVM2-class box (2 vCPU/8GB) ≈ **$7-15/mo** |
| 3 | **RAM (8GB shared across everything)** | ~8-15 tenants | Once background services + a genuinely deeper worker queue (post Rank-2 fix) are both resident, 8GB gets tight — especially if the multi-tenancy design lands on "per-tenant Hermes container" rather than "one Hermes, per-tenant session state" (per §5 of the goal plan, this choice is still open). Per-tenant containers multiply the RAM floor fast; per-tenant session state on one Hermes instance does not. | Prefer **one shared Hermes instance, per-tenant session/context isolation** over one-container-per-tenant (cheaper AND simpler) unless isolation requirements force containers; if containers are required, this breakpoint arrives much earlier (~5-8 tenants instead of 8-15). | Bump the DB/chat box to KVM4 (4 vCPU/16GB) ≈ **$13-15/mo promo** vs current KVM2 tier, only if the shared-instance design is NOT adopted |
| 4 | **Disk (screenshot growth)** | ~15-20+ tenants, but slow-moving | ~20MB/audit; at full sustained peak (20 audits/day) that's ~400MB/day (~12GB/month) against today's 30GB free — a few months of runway even at the ceiling, more at realistic average load (5-10/day). Not urgent, but worth a retention policy before it becomes an incident. | Archive screenshots >90 days to cheap object storage (Backblaze B2 or similar) instead of scaling disk; this was already going to happen for the Phase-0 backup/rsync work. | Object storage ≈ **$0.005-0.006/GB/mo** (pennies at this scale) |
| — | **Postgres** | Not a near-term breakpoint at this scale | A few hundred audit rows/year across 20 tenants with JSONB blobs is trivial load for self-hosted Postgres on the main box. No action needed until tenant count is far higher than 20. | Self-hosted stays fine; managed PG (DigitalOcean ~$15-60/mo) is optional insurance, not load-driven necessity, at this scale. | $0 required |
| — | **SimilarWeb HITL human bottleneck** | Never bites at this scale (see §1.1) | Session-lifespan-based, not query-count-based — login cadence stays ~constant regardless of tenant count. | N/A — false alarm, don't over-engineer this. | $0 |
| — | **Single Telegram bot** | Never bites at this scale | Telegram Bot API allows ~30 msgs/sec across different chats; 20 tenants' occasional status pings are nowhere near this. The real risk in this area is a **correctness** bug (session/context leakage across tenants if Hermes session state isn't properly keyed per-tenant), not a rate-limit wall — that's an architecture requirement already flagged as open in §5 of the goal plan, not a scaling breakpoint. | Per-tenant session keying (already an open design question, not new). | $0 |

**Bottom line on ranking:** the business-model ceiling (Claude subscription concurrency, Rank 1) bites *before* the hardware ceiling (Rank 2) in most realistic AE-clustering scenarios (mornings, end-of-quarter pushes), and both bite well before anything resembling a "20 tenants is genuinely a lot of data" problem (Postgres, disk) — which barely bites at all in this range. Multi-tenancy design work should prioritize the concurrency queue + subscription-capacity question first; it's the actual constraint, not the box.

All prices below are current vendor list pricing as sourced 2026-07-02 (links inline); promotional vs. renewal pricing noted where it materially differs. **Read this table with one caveat in bold:** every number in the "infra" rows (VPS, Browserbase, Clerk, Postgres, backups) is vendor-quoted and solid. The **Claude subscription concurrency row is the one genuine unknown** — Anthropic doesn't publish a concurrent-session ceiling per Max tier, so the jump from "1 subscription, flat, cheap" to "N subscriptions, $200/mo each" is a real risk to the "runtime cost ≈ subscription + pennies" assumption baked into the goal plan (§9), and it should be tested empirically (3 concurrent `claude -p` audit sessions on one Max 20x subscription, watch for throttling) before the multi-tenancy design finalizes its queue depth and cost model. If concurrency turns out to be well-supported (Max 20x handles 3-4 concurrent fine), the whole curve stays in the **$10-120/mo** range through 20 tenants — genuinely cheap. If it doesn't, subscription seats dominate the cost curve entirely and become the thing to optimize (queue-depth-1 discipline + API overflow pricing, rather than buying more $200/mo seats, is likely the cheaper fix).
