Current state (compiled truth — 2026-07-14)

Phase 2 built for real (not just planned) — 5-stage verification pipeline + per-skill dispatch, real VPS proof, plus a mid-session pivot away from claude -p as the executioner. Subagent-driven build produced prism_platform/pipeline/{gate,verdicts,self_heal,executioner,llm_stages,claims,db_write,chat_agent}.py: a real 5-stage gate (mechanical→factcheck→adversarial→quality→legal), schema-constrained per E2, wired to per-skill dispatch via self_heal.SelfHealLoop. Proven with real claude -p calls against real published audit data, not just fakes — caught 2 genuine previously-unknown data bugs (lululemon tech-stack self-contradiction; jbl's Crown-International misclassified as a JBL-owned brand when it's a sibling Harman brand) and correctly blocked a deliberately-injected fabricated claim. ~300 real tests, all passing. Found and root-fixed an unrelated, real production bug along the way: prism-runner.service ran as User=root stepping down via sudo -u chowmesadmin (an admin account) for every dispatch — this had silently broken ALL real audit dispatch (v1 and v2 alike) for 10 days via a file-permission regression nobody had hit. Fixed properly, not patched: new dedicated unprivileged chowmesuser account (no sudo group, nologin), ownership + systemd unit + dispatch code all updated, live-verified end-to-end with zero root/sudo in the chain. Two real observability gaps also fixed after Arijit caught them: job.json's phase field never updated mid-run (a real v3 audit would've been invisible for 30-90+ min) and POST /run's engine param was silently dropped (every real API caller would've quietly gotten the legacy path). One real process failure, owned directly: a renderer self-test used real skill names with fabricated PASS results — indistinguishable from a genuine report — fixed with a forced, no-default synthetic-data banner so it can't happen again. Biggest outcome of the session: Arijit's direct interrogation of each skill's real methodology (Scout usage, real network-packet inspection, SimilarWeb's permanent human-in-the-loop requirement) surfaced the actual root cause of PRISM's fabrication risk — not any skill's prompt wording, but that each skill's claude -p session decides BOTH "call the deterministic script" AND "what to do if it fails," and that second decision is where fabrication actually happens. Locked pivot: route each skill's dispatch through a deterministic Python module wherever one exists, never an LLM's call on failure — gate()/self_heal/executioner.py don't need to change, since they never cared what produces a skill's output. First one shipped for real: algolia-intel-traffic → run_traffic_module(), zero LLM calls, live-tested against the actual dead SimilarWeb key, correctly returns NEEDS_HUMAN, wired into executioner.py's MODULE_REGISTRY. 15 skills still on the old claude -p path, next session's work. The planned DSW end-to-end audit did NOT run — first blocked ~2hrs by Arijit's home network dropping to a cellular hotspot (misdiagnosed initially as a VPS-side ban, corrected once the actual gateway IP was checked), then superseded by the deterministic-executioner pivot once it was clear a real audit through the still-partially-agentic pipeline wasn't the right next step. Full detail: PIP repo SESSION.md, docs/workspace/phase2-executioner/.

Reliability crisis surfaced and partially fixed, 2026-07-09. A routine "fix Lululemon's SimilarWeb data" request turned into a 6+ hour forensic pass that exposed the real reason audits keep shipping broken: there is no single source of truth for the pipeline's code, its data, or its output shape. Three bugs found this session affect every company audit ever run, not just Lululemon — a data-quality flag that never reached the factcheck gate, a ROI calculator formula that inflated dollar-impact estimates roughly 5x, and a filename typo that has silently zeroed out the industry-benchmarks section on every single audit. The deeper cause is that the GitHub repo of skill code and the actual code running on the VPS have quietly drifted apart across roughly forty skills — one skill's instructions were caught still telling agents to use a dead, five-days-fixed API. Two skills were fixed and locked together (via a symlink, so they literally cannot drift apart again); the rest still need the same treatment. A first real step toward "the live page should just read the database" was also started: a working API endpoint that pulls straight from Postgres, verified returning correct live data — but wiring the page to actually call it hit a genuine login-session bug that was deliberately left unfixed rather than patched insecurely. A full written plan for finishing this cleanup (unify the code, move all data into the database, delete the old file-based copies, and make every skill check its own work before handing off) is saved at arijit-skills/docs/PIPELINE-UNIFICATION-PLAN.md on the VPS repo, ready for a fresh session to execute.
