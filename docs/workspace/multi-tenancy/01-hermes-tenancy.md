# Cassandra Multi-Tenancy: How 20 AEs/BDRs Each Get "Their Own Cassandra"

**Status:** RESEARCH — input to `docs/plans/multi-tenancy-architecture.md` design gate (Part 2 of the airtight-pipeline goal plan)
**Author:** research sub-agent, 2026-07-02
**Scope:** compares 3 tenancy models for the `hermes-prism` Hermes agent instance. Does not cover Part-1 pipeline/DB work (assumed shipped) or Part-4 IA re-architecture.

---

## TL;DR recommendation

**Hybrid (Model C): one shared Hermes daemon, hard per-tenant partitions in code + DB, one Telegram bot with forum-topic routing per tenant.** Not a compromise pick — it's the same design converged on independently by a comparable open-source multi-agent Telegram framework (see §5, prior art). Model A (container-per-tenant) fails on this box's RAM math before it fails on anything architectural. Model B (shared instance, session-only isolation) is what PRISM already halfway has today, and it already has a real isolation bug — the crux finding below. C fixes that bug as a side effect of doing tenancy properly.

**The crux finding, not a hypothetical:** PRISM's current single-tenant "isolation" is `_BINDINGS[session_id]` set by *content-match* on the user's message, not a hard tenant key (memory: `reference-prism-report-qa-binding`). At 1 tenant this is a UX nuisance. At 20 tenants sharing one Cassandra it is a **data leakage bug** — AE Alice could plausibly get AE Bob's account's audit content if her message content-matches his bound report, or a binding fails to confirm and silently falls through. This is the sharpest argument for *any* real tenancy model over "just let 20 people chat with the same bot" — and it's a code-level fix, not a hardware one, which is why Model A (throwing containers at it) doesn't even solve it.

## 1. Ground truth this analysis is built on (2026-07-02, verified — not re-derived)

- **Box:** single Hostinger VPS, 2 vCPU, 8G RAM, 96G disk, 30G free. 7 containers running today (Postgres, Redis, FastAPI `prism_platform`, `hermes-prism`, others), 0 failed systemd units, disk 70%. `hermes-prism` currently uses **well under 1G RAM**.
- **Cassandra = one Hermes agent instance** in container `hermes-prism`. Model `gemini-2.5-flash` today (Part 1 plans flash-lite default + pro escalation — external API calls either way, so **model tier does not change the container's own RAM footprint**, only Gemini API cost/latency).
- **State = sqlite files** (`kanban.db`, `state.db`, `response_store.db`) under `/root/.hermes-prism/` — flat files, not a server process, so "one sqlite set per tenant" is cheap (a locking/directory-layout question, not a resource one).
- **One plugin enabled:** `prism-report-qa` (588 lines) — `inject_report` + `grounding_gate` hooks, 2 audit tools. Report binding today = content-match, not a hard tenant key (see crux finding above).
- **Channels:** `cli` + `telegram` have the `prism_audit` toolset; `api_server` (web SPA) doesn't yet (Part 1 Phase 2.3 fixes this).
- **`delegate_task`** exists (`/opt/hermes/tools/delegate_tool.py`, 2956 lines), config-capped `max_spawn_depth: 1`, unused by PRISM today. Relevant to concurrency, not tenancy per se.
- **Postgres:** `audits`/`accounts`/`deliverables`/`module_executions` schema exists at alembic head, **0 rows today** — greenfield, no migration-of-live-data constraint for the multi-tenancy design itself (that's Part 3's problem).
- **Each tenant needs (per the task brief):** own conversational memory, own report bindings (only *their* accounts' audits), own Telegram bot/channel identity, and a **shared** knowledge base (Algolia sales knowledge already in Postgres, common to all).

## 2. The three models, compared

| Dimension | (A) Container per tenant | (B) Shared instance, session-only isolation | (C) Hybrid — shared daemon, hard tenant partitions |
|---|---|---|---|
| **Memory/state isolation** | Strongest — separate `/root/.hermes-prism-<tenant>/` volume, separate sqlite sets, OS-enforced | Weakest — one sqlite set, isolation is *purely* in-process session-key logic (today: content-match, provably leaky) | Strong — one process, but per-tenant directories/DB rows enforced in code + a hard tenant key (not content-match) on every read |
| **RAM at 20 tenants (this box: 8G total, ~6-6.5G usable after OS+7 existing containers)** | 20 × (current <1G baseline) = **8-15G+** just for agent processes — blows the box before anything else does. Forces a bigger box or fewer tenants. | ~1 process + N sessions' in-memory context. Realistic: baseline ~0.5-1G + ~50-150MB/active session ≈ **2-4G at 20 tenants**, fits with margin. | Same as B — one process — **2-4G at 20 tenants**, plus small per-tenant disk (sqlite files are cheap; disk isn't the constraint, 30G free). |
| **CPU at 20 tenants (2 vCPU)** | Same ceiling as B/C — containerizing doesn't add cores. 20 containers on 2 vCPUs just means worse scheduling overhead on top of the same contention. | Concurrent `claude -p` / audit-pipeline subprocesses are the real CPU cost, not chat. 2 vCPUs realistically support **3-5 concurrent heavy audit runs** regardless of tenancy model — this is a queue/scheduling problem, not a tenancy-model problem. Don't conflate the two. | Same as B. Solve with a work queue (Part 1's orchestrator state machine is the natural home for a per-tenant rate limit / global concurrency cap), not with more containers. |
| **Config/SOUL divergence** | Each container can freely diverge (per-tenant SOUL.md tweaks) — but nobody asked for 20 different personalities; Arijit's spec is ONE voice, N data scopes. Divergence risk = an unintentional drift nobody notices (20 copies of config.yaml to keep in sync on every fix). | Single `config.yaml`/`SOUL.md` — zero drift risk, but zero legitimate per-tenant customization either (fine here — customization isn't a requirement). | Single shared `SOUL.md`/model config (one voice, as designed); per-tenant *data scope* only (report bindings, memory) lives in per-tenant files/rows. Gets "one voice, N scopes" exactly right with no drift surface. |
| **Telegram bot identity per tenant** | Natural fit — one BotFather bot per container. **But: BotFather caps non-Premium accounts at 20 bots (40 w/ Premium)** [botnamefinder.com; github.com/tginfo/Telegram-Limits#288]. 20 tenants = exactly at the ceiling with zero room for AE #21 or a spare/test bot. | One shared bot, route by `user_id` → session. Works, but a single bot's DM list mixes all 20 tenants' 1:1 chats — no visual/identity separation for the AE ("is this Cassandra talking to just me?"). | **One shared bot + Telegram forum/supergroup topics, one topic per tenant** — matches a real prior-art pattern (see §5): route by `(chat_id, topic_id)`, not by raw `user_id`. Avoids the 20-bot ceiling entirely, gives each AE a distinct thread/identity, and scales past 20 without hitting a Telegram-imposed wall. |
| **Upgrade/deploy blast radius** | Smallest per-tenant (redeploy one container without touching others) but **largest in aggregate** — 20 separate deploys/restarts to roll out one fix, 20x the chance one drifts or fails silently. | Largest single blast radius — one restart takes down all 20 tenants' Cassandra simultaneously (real SPOF). Today this is already true at N=1, so it's not a new risk at small N, but it doesn't improve at N=20. | Same SPOF as B in the literal sense (one process), but the *design* pattern (gateway hot-reload, per-tenant workspace reload without full restart) is exactly what the closest prior-art proposal calls out as the mitigation (Phase 4 "resource limits and hot-reload capabilities" in the NousResearch design, §5) — buy this down with a hot-reload path, not with 20 processes. |
| **Cost** | 20x the container overhead (even "well under 1G" × 20 is real money/RAM on a box this small) — likely forces a VPS upgrade (more RAM) purely to hold idle agent processes, not to do more work. | Cheapest — marginal cost per tenant is ~100MB RAM + some sqlite rows. Model API cost (Gemini) is identical across all 3 models since it's remote either way. | Same low marginal cost as B — the "hybrid" tax is entirely in *code* (tenant-scoping logic, per-tenant directories, topic routing), not in infrastructure. |
| **Failure isolation** | True OS-level isolation — one tenant's crashed process doesn't touch another's. Best-in-class if this were the top priority. | None — a crash or an unhandled exception in one session's tool call can, in the worst case, affect the shared process for everyone (depends on Hermes's internal fault handling, not verified here — flag as an open question for the design doc). | Same technical isolation as B (one process) — the isolation that actually matters for THIS product (data isolation: tenant A never sees tenant B's data) is achieved in code, not via OS process boundaries. Crash-isolation is NOT achieved by C any better than B — call this out honestly rather than oversell hybrid. |
| **Ops burden** | High — 20x everything: 20 log streams, 20 containers to monitor, 20 potential drift points, 20 restart windows. Directly contradicts the Part 1 "self-heal must be scripted not luck" philosophy — more moving parts is more luck surface. | Low — one thing to operate, matches today's operational muscle memory exactly. | Low — still one container/process to operate; the added ops surface is a tenant-config/migration script (add-tenant, remove-tenant) which is small and testable. |

## 3. What breaks first at 20 tenants, per model

- **Model A (container per tenant):** **RAM, first and worst.** Even at a conservative <1G/container baseline (today's real number for one instance), 20 containers is 8-15G+ before any tenant sends a single message — on an 8G box already running 7 other containers. This model requires a bigger box (or a multi-box fleet) just to stand still; it doesn't fail gracefully, it fails at deploy time. Secondary failure: BotFather's 20-bot ceiling caps you exactly at the target tenant count with zero headroom.
- **Model B (shared instance, session-only):** **Data isolation, first and worst — and it's not hypothetical, it's the crux finding above.** RAM/CPU degrade gracefully (more sessions = more memory, not a cliff), but the *lack* of a hard tenant key means the failure mode is silent and dangerous: one AE seeing another's prospect data. Second-order: the shared bot's single Telegram identity gives AEs no sense of "this is my Cassandra," which undercuts the product's own framing ("her own Cassandra").
- **Model C (hybrid):** Breaks last, and along boundaries you can actually engineer around: (1) the shared-process SPOF still means one bad deploy or one runaway tool call can degrade all 20 tenants at once — mitigate with the hot-reload/per-tenant-reload pattern from §5, not by adding processes; (2) CPU-bound audit concurrency (2 vCPUs, several concurrent heavy `claude -p` runs) needs an explicit queue/rate-limit regardless of tenancy model — this is really a Part-1-orchestrator-state-machine problem wearing a multi-tenancy costume, don't let it block the tenancy design.

## 4. Per-model deep dive

### (A) One Hermes instance per tenant (container per tenant)
Each of 20 AEs gets their own `hermes-prism-<slug>` container: own config.yaml, own SOUL.md copy, own sqlite set, own bot token, own volume. This is the "obvious" cloud-native answer, and it's the wrong one *for this box*. The RAM math in §2/§3 is disqualifying on its own — this isn't a judgment call, it's arithmetic (8-15G+ of agent-process overhead alone vs. an 8G box already carrying 7 containers). It would work fine on a fleet of small boxes or with per-tenant serverless cold-start, but that's a different infra investment than "give 20 salespeople a Telegram bot," and nothing in the task brief asks for that scale of rearchitecture. Only reconsider this model if a future requirement demands genuinely divergent per-tenant configs/SOULs or hard compliance-grade isolation (e.g., a customer contractually requires physically separate compute) — neither is true today.

### (B) One shared Hermes instance, multi-session isolation
This is closest to what exists today (1 tenant, session-scoped). Scaling it to 20 by just adding more Telegram users talking to the same bot is the cheapest possible change — and it's exactly wrong because it scales the existing binding bug by 20x. `_BINDINGS[session_id]` keyed by content-match was a tolerable shortcut at N=1 (Arijit is the only user, mistakes are self-correcting). At N=20 it becomes a genuine account-data-crossing risk between AEs who have zero context on each other's book of business. Model B is not "isolation," it's "hope," and the whole point of Part 1 was to replace hope with architecture — Part 2 shouldn't reintroduce it at the tenant layer.

### (C) Hybrid — shared instance, per-tenant config/memory/toolset partitions
One Hermes daemon (keeps the RAM/CPU/ops profile of B), but tenancy is enforced as a first-class concept in code and data, not inferred from message content:
- **Hard tenant key** on every session: derive from `(telegram_chat_id, topic_id)` or `(api_server user_id)` → resolves to a `tenant_id`, looked up once at session start and carried through every hook/tool call — never re-derived by content-matching mid-conversation.
- **Report bindings scoped by tenant_id** at the DB layer: once Part 1's Postgres `audits` table is source-of-truth, add a `tenant_id`/`account_owner_id` column and enforce `WHERE tenant_id = :current_tenant` (or Postgres row-level security, a standard, well-understood mechanism for exactly this "N tenants, 1 shared DB, must never cross-read" shape) on every report/audit query the plugin issues. This is the actual fix for the crux finding — not a Telegram-layer fix, a data-layer one.
- **Per-tenant memory/state:** either per-tenant sqlite files (`/root/.hermes-prism/tenants/<slug>/*.db`) or tenant-scoped rows in a shared sqlite/Postgres table — either is fine at this scale (20 tenants, low write volume); pick whichever is less migration work off today's flat-file layout.
- **One shared knowledge base:** the Algolia sales-knowledge tables (case studies, gaps, quotes) stay exactly as they are — genuinely shared, no partitioning needed, per the task brief.
- **One Telegram bot identity, topic-routed:** avoids the 20-bot BotFather ceiling, gives each AE a distinct thread that reads like "my Cassandra," and matches a routing pattern that already exists in comparable prior art (below) rather than inventing one from scratch.

## 5. Prior art (external validation, not just first-principles)

Searched for how comparable multi-agent Telegram-bot frameworks solve this exact problem. The most directly relevant hit was an *unrelated* project that happens to share the "Hermes" name — `NousResearch/hermes-agent` (open source, not related to Chowmes-PRISM's Hermes) — which has two open design proposals that map almost exactly onto this decision:

- **["Single-Daemon Multi-Agent with Per-Topic Workspace & Memory Isolation" (issue #9514)](https://github.com/NousResearch/hermes-agent/issues/9514):** proposes consolidating a one-process-per-agent model into one gateway daemon hosting multiple agents, each with an isolated workspace/memory, routed by `telegram:topic:<chat_id>:<topic_id>` keys — i.e., Model C, independently arrived at. Their stated tradeoff: **"10x resource savings — one process instead of N for N agents"** against a real SPOF and resource-contention risk, mitigated with per-agent resource limits and hot-reload (their Phase 4) rather than by going back to N processes.
- **["Support multiple Telegram bots connecting to the same agent" (issue #8287)](https://github.com/NousResearch/hermes-agent/issues/8287):** proposes session keys of `(user_id, bot_token)` instead of `user_id` alone when more than one bot identity is needed per gateway — relevant if PRISM later wants per-tenant *bot* identity without giving up the shared-daemon RAM profile (a fallback if topic-routing turns out to feel too cramped for AEs vs. a dedicated bot). Notably scoped P3/low-priority even in that project — a signal that topic-routing (not per-user bot tokens) is the default-good-enough answer.

Two independent points of general research, cited for the specific numeric/policy claims used above:
- Telegram bot rate limits and the 20-bots-per-account (40 with Premium) ceiling: [Telegram Bot API Rate Limits Explained](https://botnamefinder.com/blog/telegram-bot-rate-limits-explained), [tginfo/Telegram-Limits#288](https://github.com/tginfo/Telegram-Limits/issues/288), [Telegram Bots FAQ](https://core.telegram.org/bots/faq).
- Container/idle-process memory overhead scales with what's inside the container, not a fixed per-container tax — i.e., "just containerize it" doesn't shrink the underlying agent-process footprint: [Docker resource constraints docs](https://docs.docker.com/engine/containers/resource_constraints/), [Docker container memory overhead](https://bobcares.com/blog/docker-container-memory-overhead/).

## 6. Recommendation

**Build Model C.** Concretely, in priority order:

1. **Fix the crux finding first, as its own small piece of work, independent of the rest of multi-tenancy:** replace `_BINDINGS[session_id]` content-match binding with a hard `tenant_id`-scoped lookup. This is valuable even at N=1 (it's a latent bug today) and is the actual precondition for C — do it before adding a second tenant, not after.
2. **Add `tenant_id` to the Postgres schema** (`audits`, and any table a tenant's data lives in) as part of Part 1's DB-source-of-truth work if not already planned — cheap now (0 rows today), expensive later (migration + backfill once populated).
3. **One Hermes daemon, per-tenant directories for memory/state** under `/root/.hermes-prism/tenants/<slug>/` — small, mechanical change from today's flat layout.
4. **One Telegram bot, forum-topic routing per tenant** (`(chat_id, topic_id)` → `tenant_id`) instead of 20 bot tokens. Keep `(user_id, bot_token)` per-tenant-bot as a documented fallback (§5, issue #8287 pattern) only if AEs report topic-routing feels insufficiently "theirs" — don't build it preemptively.
5. **Leave concurrency/queueing to the Part-1 orchestrator state machine**, not the tenancy design — cap concurrent heavy audit runs (a CPU problem) separately from tenant count (a memory/data-isolation problem). Conflating them will produce a worse design for both.
6. **Explicitly punt on OS-level crash isolation.** Model C does not give tenant-level blast-radius containment for a daemon crash — document that as an accepted risk (matches today's N=1 reality) and revisit only if uptime SLAs or compliance requirements change; don't let this table stakes into re-litigating Model A.

**Migration sketch from today's single instance (N=1 → N=20):** no data to migrate (0 rows in Postgres today), so this is additive, not a migration in the risky sense. Order: (i) hard tenant-key fix → (ii) `tenant_id` columns + RLS/scoping on the Postgres tables Part 1 is already building → (iii) per-tenant directory layout for sqlite/memory → (iv) topic-routing on the existing single bot → (v) add tenants one at a time behind a feature flag, verifying isolation (tenant A's session genuinely cannot retrieve tenant B's bound report) before onboarding the next. Each step is independently testable and reversible — no big-bang cutover required.
