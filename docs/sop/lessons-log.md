### `run-audit.sh --help` launched a real audit against a fake company — missing arg validation, not a hung-thread bug — 2026-07-02
- **Symptom:** smoke-testing the newly-deployed `run-audit.sh` v2 with `--help` (expecting a usage message) instead launched a full `claude -p` audit pipeline — real browser automation (Chrome MCP), real tool access (Apify/Crossbeam in the allowed-tools list) — researching a company literally named "--help". Arijit's first read was "the thread isn't gracefully ending, that's a resource-leak bug."
- **Root cause:** `DOMAIN="${1:-}"` only checked for EMPTY, never checked whether the argument looked like a flag. `--help` is non-empty, so it passed straight through as the domain and triggered the full-pipeline prompt. Separately (and this mattered for diagnosis): `ps -o etimes` showed the process was only 480 seconds (8 min) old when checked — well within a normal 10-90 min audit runtime — so it was NOT a hung/non-terminating thread, it just hadn't finished yet. Conflating "still running" with "won't ever end" would have led to fixing the wrong thing.
- **Fix:** added a guard right after the existing empty-check: reject any `DOMAIN` matching `-*` with `exit 64` (same usage-error convention already in the script) before it ever reaches the `claude -p` invocation. Verified negative cases (`--help`, `-h`) now reject instantly with no process spawned, and confirmed the no-args case and a normal-looking domain are both unaffected.
- **Evidence:** pre-fix and post-fix `md5sum` differ; post-fix `--help` test shows `ERROR: '--help' looks like a flag, not a domain.` exit=64, and `ps aux | grep claude` immediately after is empty (no process spawned this time, vs. spawning a full tree before).
- **Prevention (future me):** (1) before smoke-testing a script's flag parsing, READ the arg-parsing code first — don't probe blind with `--help`/`-h` assuming they're safely handled; a script that takes a required positional arg with no flag-shape validation will happily treat `--help` as real input. (2) When something "is still running and shouldn't be," check ACTUAL elapsed time (`ps -o etimes`) against the known normal duration for that class of work before diagnosing a hang — 8 minutes into a 10-90 minute process is progress, not a leak. (3) Any script accepting a required domain/identifier as arg 1 should reject anything shaped like a flag (`-*`) as its very first validation step, before any other parsing.

### Migration dry-run round-trip check catches real `Numeric(3,1)` score-precision loss (jbl, nike) — 2026-07-02
- **Context:** Built `scripts/migration/dryrun_migrate.py` — offline ETL proving all 18 published historical audits migrate into the Postgres schema faithfully, against a throwaway `postgres:16` Docker container (scratch DB only, live Postgres/VPS never touched). Round-trip verification reads every row back and deep-compares it to the source `window.AUDIT_DATA` blob.
- **Symptom:** 2 of 18 audits failed round-trip verification — jbl stored `1.9` for a source score of `1.93`; nike stored `4.3` for `4.32`. Everything else (the full JSON blob, domain, all 16 other scores) matched exactly.
- **Root cause:** `prism_platform/db/models.py` defines `Audit.score` (and `factcheck_score`) as `Numeric(3, 1)` — only one digit after the decimal. Real audit scores carry two decimal digits (calculated as `sum(score×weight)/sum(weights)`, per `10-scoring-matrix.md`), so Postgres silently rounds on insert. This is a genuine schema gap in the real table, not an ETL bug — the migration script correctly stores what it's given; the column is just too narrow for the data.
- **Fix:** Did NOT round the script's expectations to match — that would fabricate precision the source doesn't claim. Instead documented it as a blocking SCHEMA GAP in `docs/workspace/migration-dryrun/MIGRATION-REPORT.md` with the recommendation: widen `audits.score` and `audits.factcheck_score` to `Numeric(3, 2)` via an alembic migration before the real cutover.
- **Evidence:** `python3 -m scripts.migration.dryrun_migrate` output — "Round-trip PASS: 16 / FAIL: 2", with `jbl: score mismatch: stored=1.9 expected=1.93` and `nike: score mismatch: stored=4.3 expected=4.32`. Container `prism-migrate-scratch` confirmed torn down after (`docker ps -a` empty).
- **Prevention (future me):** A round-trip verification step (write → read back → deep-compare against source) is what surfaces column-width/precision bugs that unit tests on fabricated data never will — always run one against REAL historical data before trusting a schema for a real migration, and never "fix" a verification failure by loosening the check to match the lossy behavior. Ties to [[feedback-final-review-real-data]] (only real data catches buggy accessors) — this is the same principle one layer down, at the schema/column level.

### The report shows estimates as fact, false source badges, and formatting defects because provenance is never recorded — data-valid ≠ report-honest — 2026-07-02
- **Symptom (live lululemon report, Arijit's screenshots):** (1) financials EBITDA-margin line floats OFF the chart (right axis capped 0-20%, data 24-28% → line drawn above the plot box); (2) traffic section shows 30.7%/41.23%/device-split as fact, but NO SimilarWeb login was ever done for lululemon — the numbers are a silent Gemini 401-fallback estimate shown with no flag; (3) tech-stack badge says "BuiltWith" but detection actually runs via detect-search, and "Data as of —" is blank; (4) geo shows "70.9–74.43%%" / "0.9%%" — double-percent + range-concatenation formatting bugs; (5) partner data would show "Crossbeam" but Crossbeam MCP has NEVER run on any audit (all WebSearch fallback) — a Crossbeam badge is a lie.
- **Root cause:** the pipeline does NOT record real per-module provenance (actual source + method + verified-vs-estimate), and the template renders hardcoded/optimistic source badges + unflagged fallback data. So a valid-but-estimated number, or data from a fallback source, renders as authoritative fact. Separately, the mechanical factcheck gate checks DATA presence, not RENDER correctness (axis scaling, `%%`, empty dates) — so a broken render with valid data passes.
- **Fix (planned, in `docs/plans/2026-07-02-cassandra-airtight-pipeline-goal.md` §1.3b/§1.6/§2.5):** (a) record provenance per module; template renders a source badge with ✓ ONLY when data came authentically from that real source, amber "estimate/unverified" flag otherwise, never a false ✓; (b) never render a guess as fact (estimate flag or honest blank); (c) extend the gate to RENDER correctness (axis-max ≥ data-max, no `%%`/range-mash/empty-date/empty-box) + SOURCE-validity (every number has a live source that supports it); (d) Cassandra validates E2E WITH VISION (loads + looks at every rendered element) — a data-only gate can't catch an off-axis line or a `%%`; (e) self-heal loops factcheck until CLEAN, not a fixed 2 tries.
- **Prevention (future me):** (1) "the data is correct" is NOT "the report is honest" — a number can be valid, be an estimate, come from a fallback source, AND render broken, all at once. Validate DATA + PROVENANCE + RENDER + SOURCE-LIVENESS as four separate gates. (2) Source badges must be DATA-DRIVEN from recorded provenance, never hardcoded — a hardcoded "Crossbeam"/"BuiltWith" badge lies the moment the pipeline used a fallback. (3) Any number shown without a live, supporting citation is a defect, not a nicety. (4) Vision validation is mandatory for render-class bugs; field-checks are blind to pixels.

### PRISM airtightness audit: the "self-healing pipeline" is luck not code, Cassandra is a 512-token chat bot, the DB is orphaned, and there are zero backups — 2026-07-02
- **Context:** After JBL "proved" the pipeline, Arijit pushed to know whether the FULL system is actually solid (Cassandra able to run/re-run/validate/self-heal, data storage, prod-readiness). Ran a 4-agent parallel architecture audit against the live VPS. What "worked" was hiding how brittle the design is.
- **Root findings (all verified on-box, not guessed):**
  1. **Self-heal is emergent, not scripted.** `factcheck_mechanical.py` is a real deterministic blocking gate, but the BLOCKED→fix→re-run cycle that self-corrected JBL was one long `claude -p` session *happening* to retry. NO scripted retry exists anywhere in `run-audit.sh` or `prism-runner.py`. A differently-behaved run stops at BLOCKED and exits. The "self-validating loop" is a behavioral accident.
  2. **Cassandra was never built to supervise.** Model `gemini-2.5-flash`, `max_tokens: 512`; ONE plugin; exactly 2 tools (`run_audit(domain)`, `audit_status`). No re-run-skill, no validate-completeness, no re-render, no self-heal, no query tool. She "just sits there" because she has no hands, no eyes on the data, and a tiny brain — not because she's failing.
  3. **Sub-agents ARE possible but unused.** Hermes ships `delegate_task` (isolated child agents, batch/parallel), reachable on her Telegram/CLI channels, config-capped to depth-1 leaf, wired to nothing in PRISM.
  4. **No DB in the loop + zero backups.** Postgres `audits` schema exists, 0 rows; the engine never writes to it (only static sales-knowledge is seeded + read fail-open). Real system-of-record = an unbacked-up filesystem on one disk (`/opt/prism-executor/audits` isn't even a git repo). Disk failure/`docker volume rm` = permanent loss of all audit history + Cassandra's memory. Only published HTML survives (GitHub).
  5. **SimilarWeb silently broken; browser IP permanently DataDome-flagged.** Dead SimilarWeb key → Dell shipped ZERO traffic data, others guess via Gemini. No screenshot path on VPS, no HITL hook. VPS IP is DataDome-flagged; block-page screenshots (46-47KB) can slip the 50KB gate.
- **Prevention (future me):** (1) "It worked once" ≠ "it's architected" — a passing run driven by emergent LLM behavior is not a mechanism; if the retry/validation loop isn't in CODE, it isn't real. (2) Before calling any agent a "supervisor," check its actual model + max_tokens + tool inventory — a 512-token flash bot with 2 tools cannot orchestrate. (3) A built-but-empty DB (0 rows in the schema that should hold your product data) means the pipeline bypasses it — grep the execution path for DB calls before assuming persistence. (4) "Where are the backups" is a one-command check (`crontab -l`, look for pg_dump/rsync) that should run on any system claimed production-adjacent. Full remediation plan: `docs/plans/2026-07-02-cassandra-airtight-pipeline-goal.md`.
